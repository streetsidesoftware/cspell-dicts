# 0004. The friendly name, the descriptions, and where a dictionary is turned on

Status: Accepted

## Context

A dictionary names and describes itself in several places:

- **The friendly name**, such as "Australian English", is `cspell-ext.json`'s `name`. It's the title of the dictionary
  in the repo's README list, generated by `pnpm build:readme`.
- **The description** in `cspell-ext.json` follows the title in that list. Each entry in `dictionaryDefinitions` has one
  too, shown in the README's table of dictionary IDs.
- **`package.json`'s description** is what npm shows. 124 of 136 dictionaries say "for cspell" there, for example
  "Australian English dictionary for cspell.", which tells someone searching npm what the package is for.

The generator defaulted the description to "`<Friendly name>` dictionary for cspell." and used it in all three places.
10 dictionaries still carry it, 18 times in the README. In the README and in cspell's settings, "for cspell" says
nothing. The friendly name defaulted from the directory name, splitting only on `-`: `medical-terms` became "Medical
Terms", but `medical_terms` became "Medical_terms".

`languageSettings` in `cspell-ext.json` turns a dictionary on by `locale` and `languageId` (file type), where `*` matches
any. The generator defaulted both to `*`, which turns a dictionary on for every file in every language, so users get
its words wherever they spell check.

Options weighed for the description: a better generated default, which is still generic and repeated everywhere, or
keeping the default and leaving it to reviewers.

## Decision

We will:

- **Split `_` as well as `-`** in the default friendly name: `medical_terms` becomes "Medical Terms". A natural language
  name like `en_AU` still needs `--friendly-name "Australian English"`.
- **Require a written description.** `--description` has no default: with `--yes` it must be given, and the prompt has
  no default answer. It goes into `cspell-ext.json` and its dictionary definitions. "for cspell" in it is refused, with
  a message saying to describe the words instead, for example "Ruby keywords and standard library names".
- **Add `--package-description`** for `package.json`. It defaults to "`<Friendly name>` dictionary for cspell.", as on
  npm today, and the prompt asks for it with that default. The template's " -- Private until verified" stays at the end.
- **Set the locale or the file type, never both `*`.** A natural language dictionary sets `--locale`, such as `en-AU`,
  and leaves `--language-id` as `*`. Any other dictionary sets `--language-id`, such as `ruby`, and leaves `--locale` as
  `*`. Both `*` is an error: with `--yes`, one of the two must be given, and when prompting with the locale at `*`, the
  file type has no default answer and `*` is refused.

## Consequences

- The README list stops filling up with "dictionary for cspell", and every new dictionary says what words it covers.
- An agent has to write a description from its design; it can't take a default.
- npm descriptions stay consistent with the other dictionaries.
- A new dictionary is never on everywhere by accident. A dictionary that really should be on for everything is a design
  decision for a maintainer, not something the generator creates. The new-dictionary guide and skill state the same rule.
